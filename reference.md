# Справочник: артефакты OpenSpec и правила декомпозиции

Содержание:
1. Артефакты change
2. Правила декомпозиции
3. Формат источника (трассировка)
4. Нумерация и статусы
5. Приоритет источников

## 1. Артефакты change

Каталог change: `openspec/changes/<change-id>/`.

### proposal.md

Зачем нужен change и что он затрагивает. Обычно разделы:

- **Why**: мотивация;
- **What Changes**: список изменений; пометка `**BREAKING**` означает несовместимое изменение;
- **Impact**: затронутые capabilities, код, системы.

Что брать: цель, scope, out-of-scope, затронутые capabilities, breaking changes. Из proposal не выводятся подзадачи реализации напрямую, он задаёт границы: всё, что выходит за них, нужно поставить под вопрос.

### specs/<capability>/spec.md

Дельты требований. Заголовки второго уровня задают тип дельты:

| Заголовок | Смысл | Что это значит для подзадач |
|---|---|---|
| `## ADDED Requirements` | новое требование | реализовать |
| `## MODIFIED Requirements` | требование меняется (в дельте полный новый текст) | изменить поведение, обновить тесты, проверить регрессию |
| `## REMOVED Requirements` | требование удаляется (обычно с Reason и Migration) | удалить или отключить, миграция, очистка |
| `## RENAMED Requirements` | требование переименовано (FROM / TO) | обновить ссылки и документацию; отдельной реализации обычно нет |

Внутри: `### Requirement: <имя>` и под ним `#### Scenario: <имя>` с шагами `GIVEN / WHEN / THEN / AND`. Сценарии это критерии приёмки. Capability определяется по имени каталога, в котором лежит `spec.md`.

### design.md

Технический дизайн. Типичные разделы: Context, Goals / Non-Goals, Decisions (с обоснованием и альтернативами), Risks / Trade-offs, Migration Plan, Open Questions. Что брать: компоненты и их границы, интерфейсы, потоки данных, миграции и откат, риски, открытые вопросы. Файл необязателен: у небольшого change его может не быть, тогда работа идёт по specs.

### tasks.md

Чек-лист реализации: разделы `## 1. Группа` и пункты `- [ ] 1.1 Описание` (`[x]` значит выполнено). Пункты грубые или отсутствуют целиком. Это вход, а не выход: подзадачи детализируют его пункты и ссылаются на них, статусы сохраняются.

## 2. Правила декомпозиции

### 2.1. Единица подзадачи

Одна подзадача равна одной сессии работы с одним проверяемым результатом. Обычные границы: один Requirement или его отдельная часть, один компонент из design, одна миграция, один рубеж интеграции.

Подзадача должна:
- начинаться с глагола и называть результат («Добавить проверку срока жизни токена в middleware»);
- иметь источник (раздел 3);
- иметь критерий приёмки, который можно проверить;
- быть понятной без чтения остальных подзадач, кроме указанных зависимостей.

### 2.2. Размер

| Размер | Ориентир | Действие |
|---|---|---|
| S | до пары часов | нормально |
| M | до полудня | нормально |
| L | около дня | допустим, только если дальше не делится без потери проверяемости |
| больше L | нельзя | разбить |

Размеры условные и нужны, чтобы видеть перекосы, а не для планирования сроков.

### 2.3. Как разные дельты превращаются в подзадачи

- **ADDED**: минимум одна подзадача на Requirement. Если сценарии затрагивают разные компоненты, разбить по компонентам.
- **MODIFIED**: подзадача на изменение поведения плюс проверка регрессии по сценариям, которые не изменились. Если design не описывает прежнее поведение, это вопрос S-3.
- **REMOVED**: подзадача на удаление или отключение, отдельная подзадача на миграцию и очистку, если есть Migration. Без миграции при явных данных пользователей это вопрос D-3.
- **RENAMED**: подзадача на обновление ссылок и документации; если переименование не требует работы, покрытие фиксируется в матрице пометкой «без работ».

### 2.4. Сквозные задачи

Добавляй, только если этого требует design или spec, а не «на всякий случай»:

- миграция данных и схемы, откат;
- feature flag и порядок включения;
- тесты, которых не покрывают сценарии (интеграционные, нагрузочные, если design их называет);
- обновление документации и конфигурации;
- наблюдаемость (метрики, логи), если design её описывает.

### 2.5. Открытые вопросы из design

Открытый вопрос design (раздел Open Questions) обрабатывается так:

1. Ответ не влияет на состав остальных подзадач: создай подзадачу-исследование («Исследовать и зафиксировать в design: …») с зависимостью, от которой зависят затронутые реализации. Вопрос пользователю не нужен.
2. Ответ меняет состав подзадач (разные варианты дают разные задачи): это блокирующий вопрос D-2.

Не превращай открытый вопрос в реализацию одного из вариантов.

### 2.6. Порядок и зависимости

Базовый порядок: схемы, миграции, контракты и интерфейсы; затем реализация; затем интеграция; затем тесты и документация. Правила:

- зависимость указывается по id подзадачи (`Зависит от: 1.1, 1.2`), «—» значит нет зависимостей;
- циклы недопустимы;
- подзадачи без зависимостей друг от друга помечаются в разделе «Порядок и параллелизм» как параллельные;
- если порядок в tasks.md нарушает зависимости, это вопрос T-3.

### 2.7. Критерии приёмки

Берутся из Scenarios в формате `WHEN … THEN …` (при необходимости с GIVEN). Если сценариев несколько, перечисли их в одной подзадаче или разнеси по разным, но не теряй ни один. Ничего не добавляй от себя. Для подзадач-исследований приёмка описывает результат («в design.md зафиксировано решение по …»), такая приёмка допустима.

## 3. Формат источника (трассировка)

Поле «Источник» содержит одну или несколько ссылок через `;`:

| Префикс | Формат | Пример |
|---|---|---|
| spec | `spec:<capability>/Requirement:<имя>` | `spec:auth/Requirement:Session expiry` |
| design | `design:§<раздел>` | `design:§Token storage` |
| tasks | `tasks:<номер>` | `tasks:2.3` |
| proposal | `proposal:§<раздел>` | `proposal:§Impact` |

Правила:
- имя Requirement пишется дословно, как в spec; `check_coverage.py` сверяет ссылки с артефактами (регистр и лишние пробелы не важны);
- у подзадачи, вытекающей из спецификации, обязательна ссылка `spec:`;
- сквозная задача из design ссылается на `design:`;
- подзадача, детализирующая пункт tasks.md, ссылается ещё и на `tasks:`.

## 4. Нумерация и статусы

- Подзадачи нумеруются собственной иерархией `N.M` внутри групп (`1.1`, `1.2`, `2.1`). Она не совпадает с нумерацией tasks.md: связь идёт только через ссылку `tasks:<номер>`.
- Группировка: по capability, если change затрагивает несколько; иначе по компоненту или слою из design.
- Пункт tasks.md с `[x]`: все подзадачи, целиком соответствующие ему, получают `[x]`. Не снимай отметку, даже если кажется, что работа выполнена не полностью; вместо этого задай вопрос T-4.

## 5. Приоритет источников

Когда артефакты расходятся, приоритет нужен только для того, чтобы сформулировать вопрос и временное допущение, а не чтобы решить молча:

1. **specs**: что должно быть сделано (источник требований);
2. **design**: как это делается;
3. **proposal**: границы и мотивация;
4. **tasks.md**: черновой план.

Временное допущение по умолчанию: следовать специфицированному поведению (specs) и явно записать расхождение в разделе «Допущения».
